[江子社]人工智能导论

零、序

2023 年的时候，我在 OpenAI[1] 用 Google 邮箱注册了一个账号——还花了 15 大洋用于虚拟手机号接码服务，只为体验一下这个最近突然走进公众视野的新奇玩意。当时的 ChatGPT 3.5 上下文窗口既小，所能输出的文本量也少。如果你也是这一时间段体验的用户，你一定还能想起它输出到一半莫名其妙停下来，让你不得不再发一条「继续」催它干活的情景。不过无所谓，因为它带来的新奇体验能够让人忽视一切问题：多语言回复、智能对话、角色扮演[2]等等，使大家无不感叹这所谓大语言模型Large Language Model, LLM的神奇。

但是，大家不会料到一场或许能颠覆人类生产方式的革命正在悄然酝酿。

从 2023 到 2026，仿佛一切都变了，又仿佛一切都没变：娱乐变了，甚至娱乐行业也变了——首先是引发风波的是扩散模型，后来波及到音乐、视频创作；工作变了，工作方式也变了，尤其是在代码创作领域——现在就连人类引以为豪的数学也受到了巨大的冲击；甚至 AI 本身都变了：从最初的 Web 对话，Chatbot，到 Agent……但是有一件事情没变：2023 年我什么也不懂，但我能使用它；2026 年我依然什么都不懂，但我依然能使用它。

所以，这是一个艰难的决定，但我还是想尝试梳理一下我所了解和我希望了解的概念。在这个真正做到「日新月异」的领域，所有值得学习的概念都受到一个定理的支配，它名叫「只要一直懒得学，就不用学了」。不过我还是愿意相信它们中的一些能指导我了解更新的概念。

为使文章更易懂，我会尽量在概念第一次出现的时候使用被广泛认可的中文翻译。（如果真的有翻译的话）

二、智能体

从聊天机器人开始

如果你在大约 2018 年至 2022 年之间混迹于各大 QQ 群，那么你大概率见过逆流茶会家的朱鹭咲澪和朱鹭咲浅羽这一对姐妹。她们是大语言模型广泛应用之前的聊天机器人，能够与人对话，或执行一些预设的指令。

在当时，聊天机器人主要依靠人工编写的规则、关键词匹配和预设词库来实现对话。即使一些机器人允许用户自行贡献词条，它们的回答范围仍然在很大程度上受到规则和词库的限制。

后来 ChatGPT 出现，人类向机器的对话出现了新的形式：提出问题，并收到回答——且提问是自由的，不再受到之前所说词库或规则的限制。以现在的眼光来看，我们可以称这种使用方式为聊天机器人Chatbot，或者网页对话。

然而，随着大语言模型能力的不断提高，人类开始释放他们「懒」的天性：既然 AI 已经能够告诉我们如何完成任务，那为什么不让它自己去完成呢？

这就是今天的大模型使用方式，已经进入 Next Level 了：我们不再需要挑选文件并发给大模型，只需要告诉它这些东西在哪里；我们不再需要手动把大模型生成的代码复制粘贴到本地，运行后再将结果发给大模型——它自己就能完成这一系列操作，精准又高效。

这样的系统，在今天被我们称作智能体Agent，且有：

Agent=LLM+Harness \text{Agent} = \text{LLM} + \text{Harness} Agent=LLM+Harness

然而我们知道，这些功能不完全是由 LLM 提供的。LLM 可以实现对话、一部分反思和规划，并且显然无法实现 Agent Loop。因此，真正的魔法存在于这个名为 Harness 的东西中。

三、Harness

我们必须时刻谨记 LLM 是语言模型。换句话说，它只会输出文字（当然现在不止是「文字」了），其余的一概干不了。但这和我们观测到的事实相悖——Agent 既可以修改我们本地的文件，又可以执行命令行指令，甚至还可以直接操作我们的电脑[3]。为什么？

这是因为，这些操作并不是 LLM 完成的。

什么是 Harness？

假设我们要求 LLM 修改本机的某个文件，LLM 会产生相应的输出，但这些输出不会自动写入文件中，而是需要外部程序接受模型输出，并执行相应的操作。这套外部程序通常被称作 Harness。

Abstract Nonsense

据我所知 Harness 并没有可信的中文译名。我一般称之为「框架」或「模型的载体」。如果要打比方，那么 LLM 是「头」，而 Harness 是「手脚」。

理论上，一个最小的 Harness 是一个循环：调用 LLM，解析模型输出并执行，再将执行结果返回给 LLM。

沙箱与权限

然而，模型能调用工具并不代表它能操作一切，人类还没有那么傻（）

Harness 一般会允许用户控制 LLM 的权限，以及构造一个沙箱Sandbox来保护用户的设备。沙箱环境下，LLM 接触的可能是文件的副本以避免文件被 LLM 改坏。最极限的情况下，Harness 拒绝一切工具调用，这时可以认为 Agent 退化到 LLM。

但随之而来的问题是：如果有各式各样的工具操作各式各样的程序，有没有一种统一的连接规范？

模型上下文协议

有的兄弟，有的。Anthropic 发布的模型上下文协议Model Context Protocol, MCP就是一个 AI 与外部工具之间的统一连接标准。

设想这样一个场景：有很多应用都为 Agent 准备了接口，工具等等，希望 Agent 能调用它们。但对于 Agent 而言，工具虽多，要想一个一个知道它们是干什么用的很难。Harness 必须将这些应用提供的功能描述为 LLM 能理解和调用的工具，还需要处理不同应用之间的差异。如果为每一个应用单独实现一套逻辑，开发和维护的成本就会很高，这时 MCP 便应运而生了。

MCP 采用 Client-Server 架构，主要涉及三个角色：

  • MCP Host（主机）：使用 MCP 的 AI 应用，比如 Agent。

  • MCP Client（客户端）：由 Host 创建和管理，负责与某个 MCP Server 建立连接并通信。

  • MCP Server（服务器）：按 MCP 向客户端提供工具、资源和其他能力及信息的程序。

一个 Host 可以管理多个 Client，分别连接不同的 Server。

MCP 允许多种形式传输消息，比如标准输入输出，Streamable HTTP 等，这意味着 MCP Server 既可以在本地，也可以通过网络提供服务。

在连接建立后，Client 可以向 Server 查询它所提供的能力。例如一个 GitHub MCP Server 可以提供仓库读取、查看 Issue、创建 PR 等工具。

总之，MCP 为 Agent 和外部应用之间的通信提供了统一的标准，使得 Agent 的手进一步伸长了。

上下文工程

我们知道，LLM 是没有记忆的。每轮对话，我们实际上是把当前聊天窗口的所有内容整体发给了 LLM，再追加新的对话。对于 Agent，Harness 要在发起新请求时，显式提供模型需要的历史消息、工具执行结果等信息。

更重要的是，模型一次接受的信息量不是无限的，而是受到上下文窗口的限制。

因此，Harness 需要根据任务情况，对发送给模型的上下文进行组织和管理，这一过程被称作上下文工程Context Engineering。

压缩

在长时间的使用后，上下文可能超出了限制，这时 Harness 可能会主动要求模型对上下文进行压缩Compaction。通过生成摘要等方式将较早的历史记录压缩，保留重要决策和任务进度等信息。

触发压缩的阈值一般是可以通过 Harness 配置的，这一值通常小于 LLM 的最大上下文窗口。

然而，上下文工程并不能解决所有问题，因为我们希望有些信息是无损保留、永远要留在 LLM 的上下文中的。这时我们需要使用另一项重要机制——记忆。

记忆

记忆Memory是独立于模型参数的外部存储机制。Harness 可以将特定信息保存到文件、数据库或其他存储系统中，并在后续任务中反复读取。

举例来说，我们在给 LLM 立人设的时候，可以要求它将人设信息加入「长期记忆」中。在每个新对话，LLM 一般都会先读取长期记忆，了解用户的默认需求，然后再阅读用户发来的新消息。

本质上来看，记忆和其它外部信息一样，对于 LLM 而言都是「召之即来、挥之即去」的东西。但随之而来的问题是，外部信息一多，模型如何才能高效的知道自己要用哪些东西？

检索增强生成

刚才说的问题是一方面，另一方面则是：LLM 所掌握的知识来源于训练时使用的样本。也就是说，对于训练完成之后才出现的新信息，或者不在训练语料中的信息，模型是无从知晓的。

一种解决方案是：不要求模型事先记住所有的信息，而是在生成回答时，先从外部知识库检索相关资料。这种方法被称作检索增强生成Retrieval-Augmented Generation, RAG。

典型的 RAG 系统可以分为两个阶段：知识库构建和查询生成。

知识库构建

知识库构建时，系统收集需要的文档并进行预处理。通常文档会被切分称多个块Chunk，通过嵌入模型Embedding Model将各个块编码为高维向量，再将向量对应的文档信息存储到其他数据库（向量数据库）或检索系统中。

嵌入模型将文本映射到高维空间，可以使文本之间的相似度转为向量之间的相似度。因此当用户提出问题时，系统可以将问题转为向量，根据向量的相似度查找与问题最相关的若干块。

查询生成

如果问题能匹配到知识库中的块，这些内容将会被加入上下文中。LLM 再根据用户问题和参考资料生成回答。

实际上，RAG 并非必须使用向量数据库。最简单的关键词匹配或者多种检索方式的组合都可以用来构建 RAG 系统。

RAG 主要应用场景是企业内部或涉密单位。这些场景下 LLM 需要处理大量内部文件，同时在联网方面有所限制。

四、大语言模型

接下来我们把视线从我们日常与之交互的软件身上，移动到为我们不断生成答案的大语言模型上。

大语言模型和提示词

大语言模型Large Language Model, LLM是一类通过大规模数据训练、能够处理和生成自然语言等内容的机器学习模型。今天我们熟知的 GPT，Claude，DeepSeek，Qwen，GLM，豆包等，都属于这一范畴。

虽然不同模型在具体架构，训练方法和能力上存在差异，但主流的 LLM 都采用同一种内容生成方式：自回归生成Autoregressive Generation，预测下一个词元Next Token Prediction。

例如，我们向模型输入：

法国的首都是

模型会根据已有输入（词元序列），计算接下来不同词元出现的概率，并按照一定的策略选择下一个词元。对于这个例子，「巴黎」通常获得较高的概率。

词元选定后会被加入已有的词元序列中。模型根据更新后的词元序列重新按上述步骤预测后续内容，如此反复。这就是所谓「自回归」。

自回归模型的基本任务可以描述为：

P(xt∣x1,x2,…,xt−1) P(x_t\mid x_1,x_2,\ldots,x_{t-1}) P(xt​∣x1​,x2​,…,xt−1​)

其中 xtx_txt​ 表示当前需要预测的词元，x1,…,xt−1x_1, \ldots, x_{t-1}x1​,…,xt−1​ 表示此前已有的词元序列。模型根据已有的序列计算下一个词元的概率分布。

读到这里，你可能会产生疑惑：如果 LLM 只是一个不断预测下一个词元的模型，它为什么能够回答问题、编写程序，甚至进行复杂的数学推理？

在此之前，你可能还有一个更想问的问题：依靠概率选择回答，靠谱么？

我们先来回答后面这个问题：依靠概率选择回答，一点也不靠谱。这就引出了全世界最顶尖的学者仍然奋力研究的问题、坑害过无数对 LLM 原理不了解的人的问题——幻觉Hallucination。

幻觉

模型幻觉指的是模型生成了看似合理通顺，但不符合事实或者缺乏依据的内容。例如，在回答学术问题时，模型引用了一篇不存在的论文，却能够信誓旦旦地说出它的内容，甚至还能编造出发表年份和作者。

为什么会出现幻觉？最大的原因是 LLM 的训练目标并不是生成与事实完全一致的文本。对于自回归语言模型而言，预训练的目的是让模型学习文本序列的概率分布，而不是逐条验证其表述是否为真。一个句子即使在语言上十分自然，也不意味着它的表述就必然正确。

比如：

我姓李。

和

我姓王。

这两句都是符合语法的句子，但在一个确定的上下文中，至少有一句是错误的。

除此之外，训练数据本身也可能存在错误或偏差。当面对知识之外的数据时，如果模型不能发现这一点并说明「我不知道」时，它将持续生成内容直到结束[4]，详参词元一节。

以现在的架构，幻觉是无法消除的。我们可以通过之前介绍的 RAG 等方法减弱模型的幻觉。类比人类来说，你在遇到不会的问题时，可以大大方方说「不知道」，而模型如果没能把「不知道」说出口，就会硬着头皮一直编下去。

回到原来话题：为什么 LLM 可以通过「预测」来实现智能呢？简单来说，为了完成预测任务，模型会从大量的训练数据中学习语言的结构、不同概念之间的关系，以及数据中包含的各种规律。随着训练规模的扩大，这些能力可以被引导，甚至自发迁移到别的领域。我们将在训练中探讨这一神奇的现象。

提示词工程

接下来我们回归日常使用 LLM 的场景。当我们向 LLM 发送一条消息时，实际上我们在向 LLM 提供一段输入内容。LLM 根据这段输入和其他上下文，通过自回归生成后续的回答。

提供给模型的输入内容被称作提示词Prompt。

Prompt 可以是一句简短的问题，也可以是长篇大论；可以是含糊不清的，也可以是一五一十的。最重要的是，Prompt 可以是自然语言的，也可以是结构化（例如使用类 JSON 结构）的。设计和组织提示词，引导模型按照预期完成任务，这项操作被称作提示词工程Prompt Engineering。

最简单的一种提示词工程是少样本提示Few-shot Prompting，即在提示词中加入少量的输入输出样例，让模型根据提示来完成类似任务。比如：

你是一个导数领域大神。当我说出原函数时，你会马上准确无误的说出它的导函数。比如我说：sin(x)，你会回答 cos(x)。

提示词工程已经深入我们的日常使用中，以至于我们几乎不用刻意注意这件事。现代 LLM 的输入已经具有一定的结构，比如一次模型请求可能包括 System（系统提示词），User（用户输入）等不同字段，以及各种调用工具的提示。古代（hhh）使用 LLM 时，用户可能还得手动将自己的输入转成格式化的输入，进行「古法」提示词工程，现在这种行为基本上已经消亡了。

词元

3 月 23 日中国发展高层论坛 2026 年年会上，国家数据局局长刘烈宏正式公布，AI 领域核心概念 Token 的标准中文译名为词元[5]。

下文中以 Token 表示这一概念。

我们知道不论文本还是图像都需要转换成数字，才能参与神经网络[6]计算。然而，不同语言的「字」或「单词」概念不一样，没法以一个人们生活中既常用、又通用的方法来处理文本。所以我们让 LLM 先使用分词器Tokenizer将文本转为一系列词元Token，再来处理。

Token 是模型处理文本时使用的基本离散单位。

Token 不等于一个字或一个词。它有时等于一个词组，有时又等于一个单词词缀——这取决于 Tokenizer。比如 “preview” 很有可能被分成 “pre” 和 “view” 两个 Token，而「中国」往往就是一个 Token。

分词算法

现代 LLM 常见的分词算法包括字节对编码Byte Pair Encoding, BPE、WordPiece 和 Unigram 等。它们通常基于训练语料中的统计规律，构建一套有限的词元词表（Vocabulary）。

以 BPE 为例，其基本思想是通过反复合并频繁共同出现的相邻单元，逐步构建更大的词元。因此，常见的字符组合或单词可能被表示为较少的 Token，而罕见的词语则可能被拆分成更多部分。

Tokenizer 会将文本转换为词元序列，再根据词表映射为相应的整数编号，通常称为 Token ID。

对于 LLM 而言输出则相反：模型实际上预测的是 Token ID，经过解码后将对应的文字呈现给用户。

因此，Token 既是模型处理文本的基本单位，同时也是衡量输出长度的标准。这就是为什么模型 API 大多按 Token 计费，我们看到的用量也是以 Token 为单位。

Attention

有两点需要注意：

  1. 不同模型的 Tokenizer 很可能不同，因此一段文本被分成多少 Token、每个 Token 是什么，很可能是不同的。

  2. Token 不一定对应文字，还有可能对应标点、空白等等。

特殊词元

词表中有一些 Token 不代表文本，而是用来控制输出流、或起到其它特殊作用的。这类 Token 被称作 Special Tokens。

自回归语言模型不知道自己什么时候该停下。如果没有一个标记，它将一直自回归生成内容直到大道磨灭。因此我们引入 <EOS>（End of Sequence）这类特殊 Token，用来标记内容完毕。当模型输出 <EOS> 时，停止输出。

Hint

然而，模型输出还受到最大输出 Token 限制的影响。因此不会真的无限输出下去。

上下文窗口

在前面的介绍中，我们知道模型会根据已有的 Token 序列预测下一个 Token。那么，模型到底能根据多少 Token 去预测呢？

LLM 在一次推理中能够处理的 Token 序列长度是有限的，这个限制被称作上下文窗口Context Window。也就是说，模型并不能参考无限长的上下文。上下文窗口的单位也是 Token。

模型支持的上下文一般是 2 的幂次，比如 128K（128 * 210）。上下文不仅包含用户当前的输入，还包括历史输入输出、系统提示词、工具调用结果等等。

上下文窗口是极难增长的。这是因为目前主流的 LLM 大多基于 Transformer 架构，其核心机制是注意力Attention机制。如果输入序列长度为 nnn，注意力计算涉及到一个 n×nn \times nn×n 的矩阵，因此计算的时间复杂度会包括 O(n2)O(n^2)O(n2) 的部分。

有时我们会看到某些模型鼓吹自己拥有 1M（1 * 220） 上下文。对于用户来说，模型能记住更多信息，这固然是好的。但是上下文窗口变大，意味着模型能够充分利用其中的所有信息吗？

长上下文的有效性

2023 年发表的论文 Lost in the Middle: How Language Models Use Long Contexts 表明在所测试的一些模型和任务中，当相关信息位于上下文的开头或结尾时，模型往往表现更好；信息在上下文中间时，模型表现可能下降。这一现象叫做中间信息遗失Lost in the Middle。

由此我们知道，尽管模型可以接受长上下文，但是并不一定能充分利用上下文中的有效信息。所以没必要无脑选标称「超长上下文」的模型，压根没必要把一切都塞进上下文窗口中。

思维链

接下来要介绍的东西是当今大模型拥有「智能」的基础。试想这样一个场景：两个 LLM 做数学题——一个没有过程，直接出答案；；另一个则洋洋洒洒写了好几页过程，最后出答案。你会更相信哪一个模型的结果呢？

事实上，人们在模型幻觉这个问题上已经吃过很多亏了，每个人都小心翼翼、如履薄冰，追求模型用更详细的方法给出答案，而且最好是能让人看到解答过程的。在这样的背景下，Google Research 等机构的研究人员提出了改善大语言模型复杂推理任务表现的方法——思维链Chain of Thought, CoT。

所谓思维链，就是模型在生成最终答案前，先生成一系列中间推理和思考的步骤。这一概念非常像我们做题时在草稿纸上写的中间解题步骤。你可能会有疑惑：不就是多生成了一些文字吗，为什么会提升最终结果的正确性呢？

别忘了，我们的 LLM 是自回归模型。每生成一个 Token，这个 Token 都会加入 Token 序列，去影响下一个 Token 的生成。也就是说所有的中间输出都会作为最终输出的一个「基础」。

例如我们问模型：

仓库中有 18 箱书，每箱 24 本，现在运走了 175 本，还剩多少本？

运用 CoT，模型可以先生成：

首先，仓库中原有 18 × 24 = 432 本书。
然后，运走 175 本后，还剩 432 − 175 = 257 本。
因此，答案是 257 本。

最后，模型再输出一个答案：

仓库还剩 257 本书。

思维链提示

接下来依旧是古人的智慧：运用提示词工程引导模型的思维链。

思维链提示Chain-of-Thought Prompting 可以看作是一种特殊的少样本提示：我们在提示词中还加入少量 CoT 的样例，引导模型按这个步骤思考。

后来人们发现，即使不提供思维链示例，只是要求模型 “Think step by step”，也能改善模型的表现。这被称作零样本思维链Zero-shot CoT。

推理模型

然而，光有 CoT 这一技术是不够的。我大可以写一个系统提示词，让 LLM 在回答问题时先输出一堆思考过程，再给出一个答案。但真正的 LLM 显然不是这么运作的。

我们要做的，实际上是在训练阶段就让模型掌握更有效的「推理」方式。可以说是让模型养成「先想步骤再作答的习惯」，而不是仅仅依靠提示词引导模型。

2024 年 9 月，OpenAI[1:1]发布了 o1 系列模型，具备推理Reasoning能力。

与此前 LLM 追求快速反应相比，o1 的一个重要特点是模型在给出最终答案前会生成较长的推理过程，并在必要时调整解答策略。

当此之时，o1 的发布震动了全球的大模型领域，并催生出了 “o1-like” 这个词来形容具有 o1 这种推理能力的模型。今天我们知道，这类经过专门训练，能在复杂任务中投入算力进行推理的模型，叫做推理模型Reasoning Model。

DeepSeek-R1: 通过强化学习获得推理能力

接下来登场的是——闷声发大财、小钱办大事、救 Anthropic 于水火、让梁爷爷击落英伟达股价、将推理能力带给无数模型的 DeepSeek-R1。

2025 年 1 月，DeepSeek 发布论文 DeepSeek-R1: Incentivizing Reasoning Capability in LLMs via Reinforcement Learning，展示了强化学习在提升大语言模型推理能力方面具有很大的潜力。

其中论文介绍了 DeepSeek-R1-Zero 的训练方式：模型以预训练后的基础模型为起点，进行大规模强化学习，而没有事先通过监督微调向模型提供完整的推理过程样例。

训练中，模型会针对数学、编程等任务生成答案，再根据答案的正确性和格式获得相应的奖励。

随着强化学习的进行，R1-Zero 开始表现出更长的思维链，并出现了自我验证、反省等行为。最有意思的是模型会突然开始审视之前的推理过程，意识到可能存在问题，然后尝试另一个方法。研究人员称之为顿悟时刻Aha Moment。

Abstract Nonsense

DSR1 值得被提及，不仅是因为它以极低的成本实现了推理模型，而且是因为它公布了训练方式、开放了模型权重。作为开源事业的支持者，我真得表扬你了，真的。

长推理的有效性

这一部分道理很简单。推理是为了提高复杂任务的正确性。对于十分简单的任务，生成一大堆思考过程没有任何意义，只会平白无故增加成本。另外大家也一定被模型动不动就进行一个「雷霆」大思考困扰过。过度思考不仅拖慢任务进度，也可能让模型做出不必要的设计。

所以，能开 high 搞定的活，就没必要开 xhigh 甚至 ultra 了，可能适得其反哦。

五、模型推理

刚看完上一节的你，看到这一节的标题一定会感觉很疑惑：「推理模型」和「模型推理」有什么区别？这两个名词如此相像，主要还是中文翻译的锅。

模型推理Inference和推理Reasoning模型是完全不同的概念。前者「推理」的意思是使用训练完成的模型，根据输入执行计算，产生输出。通俗的来说，就是大模型产生回答的过程。
